**Training feasibility and proposed research.** The official trainer supports
[importing `.nnue` and exporting `.pt`/`.nnue`](https://github.com/official-stockfish/nnue-pytorch/blob/aa2fff2f4a67d1a268dad991fcc03430781fde15/serialize.py),

[QAT](https://github.com/official-stockfish/nnue-pytorch/blob/aa2fff2f4a67d1a268dad991fcc03430781fde15/model/config.py),
and distributed training. Importing a released quantized network is a warm
start; it does not recover the original optimizer state or discarded precision.
Architecture and feature configuration must match before importing it.

Training weights is practical with AWS. Exceeding current mainline strength is
a harder research target given its data scale. The first milestone should be
a reproducible train/export/play loop with a compatible baseline and separate
validation data. The current trainer can reuse training data for validation
unless separate validation datasets are explicitly supplied.

| Direction | Proposed experiment | Success criterion |
| --- | --- | --- |
| Exact inference optimization | SIMD scheduling, cache/update paths, sparse layers, register pressure, and layout on a fixed target CPU. | Exact outputs plus a repeatable speed gain under the frozen evaluator. |
| Smaller trained networks — strongest extension | Distill a strong teacher into narrower or structurally sparse networks; use QAT and CPU-friendly dimensions. | Better playing strength at equal wall-clock time, accounting for faster search. |
| Training data and recipe search | Compare data mixtures, phase balance, difficult-position sampling, loss mixtures, and schedules with repeated seeds. | Held-out match improvement; validation loss alone is insufficient. |
| Neuron ordering and block sparsity | Improve target-specific packing against the existing `ftperm.py` baseline. | Exact-output validation where applicable and measured target-CPU gains. |
| Faster training pipeline | Profile sparse feature-transformer kernels and data loading, then optimize actual bottlenecks. | More useful training throughput with equivalent training behavior. |

The [existing feature permutation tool](https://github.com/official-stockfish/nnue-pytorch/blob/aa2fff2f4a67d1a268dad991fcc03430781fde15/ftperm.py)
already optimizes zero blocks. Changing serialized weight order requires a
separately scoped experiment because the original task freezes network bytes.

Use gradient-based optimization for millions of weights. Shinka can search the
outer choices: training recipes, architectures, data selection, and kernels.
Changing weights alone generally leaves the arithmetic cost of a fixed dense
architecture unchanged, although activation sparsity can affect runtime.
Training smaller or more exploitable structures connects training to the
original inference-speed goal.

Learned weights intentionally change evaluation outputs, so they need their
own benchmark contract. Use paired games with colors reversed, independent
opening sets, fixed engine/search settings, and preregistered statistical
criteria. Fixed-node tests help separate evaluation quality from speed;
equal-time matches measure the actual combined benefit. Finalists need fresh
tests after selection. Stockfish's
[Fishtest methodology](https://official-stockfish.github.io/docs/fishtest-wiki/Fishtest-Mathematics.html)
uses paired-outcome modeling and sequential testing; tiny Elo differences may
require large match budgets.

**Follow-up: verification, individual fitness, and alternative Shinka targets.**
The user subsequently asked how to verify trained weights, score individuals,
whether inference-only evolution is worthwhile, and whether search must evolve
with NNUE. The following is a proposed evaluation design, not an implemented
evaluator or a completed experiment.

Keep separate campaigns for exact-output implementation changes and learned
evaluation changes. An inference individual is a code patch with the network
frozen. A training individual is a recipe/architecture plus its trained artifact
and manifest. Backpropagation trains weights; Shinka changes the outer recipe
or code. For recipe comparisons, use the same initial checkpoint and declared
training budget. Confirm leading recipes with independent training seeds;
many games for one checkpoint do not measure training-seed variability.

| Campaign | Proposed scalar fitness | Other recorded evidence |
| --- | --- | --- |
| Exact NNUE implementation | Exponentiated lower 95% bound of the paired mean log speedup, following the existing forward-path plan. | Raw timing pairs, workload totals/call counts, correctness, memory, and full-engine speed. |
| Trained weights or architectures | Lower 95% bound of expected game points against a frozen baseline at the target time control. | Win/draw/loss and paired-outcome counts, game count, uncertainty, validation loss, latency, training cost, and artifact hashes. |
| Search behavior changes | The same match-based fitness with network and other engine settings frozen. | Nodes, evaluations, time use, crashes, and regression slices. |

For matches, the underlying mean is `(wins + draws / 2) / games`; 0.5 is neutral
against the reference in expectation. Estimate uncertainty using independent
opening pairs, with colors reversed, rather than treating the paired games as
independent. A conservative bound above 0.5 supports a positive result under
that test. An operationally valid but weaker network remains `correct=true`;
it gets a lower score. Do not confuse model quality with execution correctness.

Start with equal game budgets for individuals scored at the same stage. If
sampling adaptively, use an appropriate sequential method; repeatedly checking
ordinary fixed-sample 95% intervals invalidates their nominal coverage. SPRT is
useful for promotion/rejection, but its log-likelihood ratio is not a comparable
population fitness. Keep the reference engine fixed through a campaign:
win rates measured only against each candidate's parent are not comparable.

A training candidate should pass these stages:

1. Artifact and inference checks: export/load, architecture compatibility,
   quantized-reference agreement, incremental-versus-refresh agreement, undo
   behavior, resource limits, and engine stability. Its outputs are expected
   to differ from the old network.
2. Cheap screening on held-out teacher targets, calibration, and error slices.
   Split by games or source groups to avoid leaking adjacent positions. These
   checks are proxies; lower validation loss does not prove higher Elo.
3. Paired engine matches on identical hardware/settings at the target wall-clock
   time control. Fixed-node matches are a useful diagnostic to suppress the
   speed advantage, but do not replace equal-time testing of faster networks.
4. Fresh finalist matches on unused opening sets, intended longer controls,
   and multiple training seeds when claiming a recipe improvement. Repeatedly
   queried search-validation data is not the final test set.

Use cheap checks to eliminate broken or clearly poor candidates and allocate
large match budgets to plausible improvements. Small Elo differences can need
tens or hundreds of thousands of games or more. The required budget depends
on effect size, paired-outcome variance, draw rate, and error tolerances.
Do not make short-time-control performance the only gate for architectures
intended for long thinking times: the accepted
[SFNNv16 update](https://github.com/official-stockfish/Stockfish/commit/f4bcd40409f94bd397a083c5d6243bac6dcc6d85)
failed its STC test and passed LTC after 189,888 games.

Inference-only optimization is a valid target. Unchanged evaluations can be
computed more cheaply without changing search policy. There is recent evidence:
an accepted [king-move accumulator optimization](https://github.com/official-stockfish/Stockfish/commit/db98633b1f8bbcad850bee892ec143ff8723ba80)
reported about 0.60% local speedup, and
[fused AVX2 activations](https://github.com/official-stockfish/Stockfish/commit/1c384d3a8774ec9906e2e85b5005b22e27489044)
reported about 2.45% on its tested machine. Both were non-functional changes.
They are already merged and are evidence of feasibility, not improvements
available to claim again or estimates of M2 headroom.

Score inference candidates on real search-shaped traces, then verify finalists
in the whole engine: cache effects can defeat an isolated microbenchmark gain.
The total benefit is limited by the runtime fraction spent in NNUE. As an
illustration, a 1.2x NNUE speedup with 60% of runtime in NNUE gives approximately
1.11x whole-engine speedup before other effects. That fraction has not been
measured for our workload.

Additional research angles worth comparing:

- Exact SIMD kernels, sparse-layer execution, and neuron/block ordering.
- Exact accumulator policies: when to refresh versus incrementally update,
  cache layout, and feature-update scheduling.
- Architecture and feature design that balance accuracy against the cost of
  updating features after a move, rather than considering network width alone.
- Search-aware training data: emphasize evaluation errors near costly pruning
  decisions while keeping search fixed; validate the hypothesis in games.
- Focused search-rule changes, such as move ordering or reduction/pruning
  formulas, with a fixed network. Use SPSA or another inexpensive optimizer
  as a baseline for tuning constants; reserve Shinka for structural proposals.
- Faster trainer kernels/data loading, scored on throughput under a training
  quality constraint, to increase the number of experiments AWS can support.

Search coevolution is unnecessary for exact-output speedups. For changed
weights, the interaction is real: current `search.cpp` uses static evaluations
in null-move reduction and futility thresholds, while `evaluate.cpp` applies
search-dependent scaling. First test the new network under unchanged search,
then tune a small declared interface. Compare all four combinations of old/new
network and original/tuned search to establish whether an interaction helps.
This is more interpretable than changing both systems throughout one campaign.

Equal-time match strength already includes inference speed. Do not add a
separate NPS reward to that score and inadvertently count speed twice. If
multiple latency/strength tradeoffs matter, retain a Pareto set and declare
the deployment constraint. AWS CPU fleets are well suited to independent match
pairs; GPU fleets handle training and teacher labeling. More compute improves
coverage and statistical precision, but cannot repair a misaligned objective.
